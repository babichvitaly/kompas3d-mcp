# Наша установка и ближайшие задачи

Дата проверки: 2026-10-09. База исходного проекта:
`76cf2935bed3e2b16a0285964bfb2d80e570238b`.

## Рабочая схема

Mac → Parallels Desktop → Windows 11 ARM → Codex → локальный MCP → КОМПАС.
КОМПАС-3D: 25.0.0.2735, 64-bit. Python: 3.12.15 x64, работающий в Windows ARM.
MCP предоставил 41 инструмент. Отдельный сервер/VPS для этой схемы не нужен:
COM вызывается внутри Windows, где установлен КОМПАС.

После подключения форка в Windows: `ruff` прошёл, `pytest` — 16 тестов прошли,
MCP из editable-установки вернул 41 инструмент и подключился к КОМПАС v25.

Windows-копия расположена в `%USERPROFILE%\Documents\CodexCAD\kompas3d-mcp`.
Тестовые модели и отчёты находятся рядом в `CodexCAD\test-output`, вне Git.
Мак-копия подходит для работы с исходниками, но проверка COM требует Windows.

## Разработка в Windows

Открой папку репозитория в Codex. Стандартные команды из CONTRIBUTING.md:

```powershell
uv sync --locked
uv run ruff check src tests scripts
uv run pytest -q
```

В текущей установке зависимости были перенесены с Mac из-за тайм-аутов загрузки
в Windows. Окружение сохраняется в `.venv`, пакет устанавливается в editable mode.
Проверить, откуда Python читает код:

```powershell
.\.venv\Scripts\python.exe -c "import kompas_mcp; print(kompas_mcp.__file__)"
```

Ожидается путь в `src\kompas_mcp`, а не копия в `site-packages`.
Изменения Python вступают в силу после перезапуска MCP в Codex.
При изменении навыков обнови их установленную копию через
`scripts/install.py --update-skills` согласно README.

Изменения ведём в своей ветке `codex/windows-kompas25`.
`origin` указывает на наш форк, `upstream` — на проект автора.
В Windows установлен Git ARM64. Публикация изменений пока выполняется из
авторизованного GitHub-сеанса на Mac. Для прямого push из Windows потребуется
отдельный вход в GitHub; данные доступа с Mac туда не переносились.
Не обновляй одновременно две рабочие копии с несохранёнными изменениями.
Перед обновлением выполни `git status`; обновления автора сначала сравни:

```powershell
git fetch upstream
git log --oneline HEAD..upstream/main
git diff HEAD...upstream/main
```

## Что подтверждено

На синтетической пластине выполнена последовательность через настоящий MCP:

1. Создание эскиза 80 × 50 мм и выдавливание на 8 мм; объём 32 000 мм³.
2. Изменение переменной глубины до 12 мм; объём 48 000 мм³.
3. Сохранение M3D, закрытие и повторное открытие.
4. Проверка одного тела и габаритов 80 × 50 × 12 мм, получение PNG.

Это подтверждает данный простой сценарий, а не готовность любых деталей,
сборок и чертежей. Исходные пользовательские документы не использовались.

## Первая задача: пустые стандартные виды

Воспроизведение: создать CDW и вызвать `create_standard_views` для сохранённой
пластины, проекции `front`, `top`, `left`, затем сохранить и открыть CDW.

Наблюдается: появились три ассоциативных вида, но в них нет геометрии;
в дереве видны красные маркеры. Путь `SourceFileName` соответствует модели.
После перестроений `ObjectCount=0`, `Valid=True`, `TreeNeedRebuild=True`.
Проверены `IAssociationView.Rebuild`, `IKompasDocument2D1.RebuildDocument`
и `IDrawingDocument.RebuildViews`: успешный BOOL не устраняет пустые виды.

Ошибка первоначальной проверки: число видов и успешное сохранение были
приняты за достаточное подтверждение. Визуальная проверка это опровергла.
Результат CDW не считается пригодным для использования.

Дальше: сравнить создание вида вручную и через API; проверить путь/проекцию,
свойства источника, `Update` и порядок перестроения по установленному SDK.
Причина пока не установлена. Не добавлять обходной путь без живой проверки.

Критерий готовности: видимая геометрия нужных проекций; отсутствие ошибки
перестроения; сохранение связи с моделью после открытия CDW; изменение
толщины модели корректно обновляет вид. Проверять результат на экране,
по доступным объектам/геометрии и после сохранения, а не только по BOOL.
