# Наша установка и проверенный процесс работы

Дата проверки: 9–10 октября 2026 года. Рабочая ветка: `codex/windows-kompas25`.
База исходного проекта:
`76cf2935bed3e2b16a0285964bfb2d80e570238b`.

## Рабочая схема

Mac → Parallels Desktop → Windows 11 ARM → Codex → локальный MCP → КОМПАС.
КОМПАС-3D: 25.0.0.2735, 64-bit. Python: 3.12.15 x64, работающий в Windows ARM.
MCP предоставил 41 инструмент. Отдельный сервер/VPS для этой схемы не нужен:
COM вызывается внутри Windows, где установлен КОМПАС.

Проверки форка: `ruff` прошёл, `pytest` — 26 тестов прошли на Mac и Windows.
Настоящий MCP из editable-установки вернул 41 инструмент и подключился к КОМПАС v25;
через stdio созданы три точные проекции с четырьмя линиями в каждой.

Windows-копия расположена в `%USERPROFILE%\Documents\CodexCAD\kompas3d-mcp`.
Первые тестовые модели находятся рядом в `CodexCAD\test-output`, вне Git.
Новые приёмочные сценарии пишут отдельные комплекты в `artifacts` внутри репозитория;
этот каталог исключён из Git.
Мак-копия подходит для работы с исходниками, но проверка COM требует Windows.

## Разработка в Windows

Открой папку репозитория в Codex. Стандартные команды из CONTRIBUTING.md:

```powershell
uv sync --locked
uv run ruff check src tests scripts
uv run pytest -q
```

В текущей установке зависимости были перенесены с Mac из-за тайм-аутов загрузки
в Windows. Окружение сохраняется в `.venv`, пакет устанавливается в editable mode.
Проверить, откуда Python читает код:

```powershell
.\.venv\Scripts\python.exe -c "import kompas_mcp; print(kompas_mcp.__file__)"
```

Ожидается путь в `src\kompas_mcp`, а не копия в `site-packages`.
Изменения Python вступают в силу после перезапуска MCP в Codex.
При изменении навыков обнови их установленную копию через
`scripts/install.py --update-skills` согласно README.

Изменения ведём в своей ветке `codex/windows-kompas25`.
`origin` указывает на наш форк, `upstream` — на проект автора.
В Windows установлен Git ARM64. Публикация изменений пока выполняется из
авторизованного GitHub-сеанса на Mac. Для прямого push из Windows потребуется
отдельный вход в GitHub; данные доступа с Mac туда не переносились.
Не обновляй одновременно две рабочие копии с несохранёнными изменениями.
Перед обновлением выполни `git status`; обновления автора сначала сравни:

```powershell
git fetch upstream
git log --oneline HEAD..upstream/main
git diff HEAD...upstream/main
```

## Исправление пустых видов

`AddStandartViews` наследовал черновое проецирование (`IAssociationView.UseOcclusion=True`).
В проверенной установке метод возвращал True и создавал три вида с `Valid=True`,
но `ObjectCount=0`. Точное проецирование с последующими `Update()` и `Rebuild()`
каждого вида создаёт реальные линии. Внутренняя причина сбоя чернового проецирования
не установлена; это наблюдение не доказывает проблему всех установок Windows ARM.

`create_standard_views` теперь по умолчанию задаёт `draft_projection=False`,
возвращает созданные виды и проверяет их количество, валидность и наличие объектов.
Существующие виды определяются по `Reference` и не меняются. Частичный результат
при ошибке остаётся в документе и описывается в ответе — перед повтором его нужно изучить.
Черновой режим доступен явно через `draft_projection=True` и проходит те же проверки.

Наличие объектов — базовая проверка, а не подтверждение правильной геометрии.
Приёмочные сценарии дополнительно измеряют линии, размеры, объём и проверяют
сохранение/открытие. `TreeNeedRebuild` и `IPart7.NeedRebuild` управляют автоматическим
перестроением дерева/модели при изменении свойств; True не означает ошибку геометрии.

## Обновление модели и связанного чертежа

На этой установке повторная перезапись одного M3D может оставить устаревшие
проекции: в цикле 8→12→16→12 мм модель уже имела толщину 12 мм, а виды сохраняли
16 мм после успешных вызовов перестроения. Такой же сбой воспроизведён без размера,
поэтому размерная связь не является его причиной. Для проверенного примера помогает
новая редакция файла с перепривязкой существующих видов.

1. Определи документы и все связанные источники. Подготовь отдельный рабочий
   комплект; для сборки одной копии A3D недостаточно.
2. **До следующего изменения** сделай побайтовую копию текущего сохранённого M3D
   под уникальным именем редакции, например `plate-rev-02.m3d`. Проверь совпадение
   SHA-256 копии и предыдущей редакции; существующие файлы не перезаписывай.
3. Открой новую редакцию, измени её параметр, перестрой и проверь геометрию.
   Сохрани и повторно открой M3D, чтобы проверить результат на диске. Убедись,
   что SHA-256 предыдущей редакции не изменился. Новый файл становится связанным
   источником результата; следующее изменение снова начинается с отдельной копии.
4. Найди **все виды данного источника** в рабочем CDW. Запомни их `Reference`
   в текущем сеансе и существующие размеры. Для каждого вида задай
   `IAssociationView.SourceFileName` новой редакции и вызови `Update()`.
5. После обновления источника у всех этих видов вызови `Rebuild()` каждого,
   затем `IKompasDocument2D1.RebuildDocument()`. Перепривязка использует
   существующие виды и размеры; пересоздавать их для обхода сбоя не требуется.
6. Проверь фактический источник каждого вида, геометрию проекций и значения
   связанных размеров. В текущем сеансе проверь сохранение исходных видов.
   Сохрани и повторно открой CDW, затем повтори проверки. COM-идентификаторы
   после закрытия документа могут измениться.

Итоговый комплект должен содержать CDW и новую редакцию M3D, на которую он ссылается.
Результат этого процесса проверен на пластине с тремя видами и одним размером.
Он не исправляет сам механизм обновления по прежнему пути и требует отдельной
проверки зависимостей и размерных связей на сложных документах.

## Что проверено на синтетических документах

- Нативная пластина 80 × 50 × 8 мм: эскиз, выдавливание, переменная толщины.
  Изменение рабочей копии до 12 мм даёт одно тело и объём 48 000 мм³.
- Три точные проекции содержат по четыре стороны прямоугольника. После сохранения
  и открытия остаются геометрия и ссылка на источник.
- Полный цикл толщины 8→12→16→12 мм прошёл: после первого изменения до 12 мм
  каждый следующий шаг выполнялся в новой копии источника, созданной **до** правки.
  Те же виды и ассоциативный размер сохранились; конечные геометрия, источник
  и размер 12 мм проверены после открытия CDW. Координатный размер привязывается к ребру через
  `IDrawingObject1.NewConstraint`; само создание размера привязку не гарантирует.
- Сборка содержит одну внешнюю связанную деталь. Изменение её копии с 8 до 12 мм
  обновляет сборку с 32 000 до 48 000 мм³. При плотности 7,85 г/см³ масса изменяется
  с 0,2512 до 0,3768 кг. Путь компонента и значения проверены после открытия A3D.
- SHA-256 исходного M3D, базовой рабочей версии 12 мм и обеих сохранённых редакций
  проверены: последующие действия их не изменили.

Полный приёмочный прогон `scripts/validate_associative_drawing.py`:
`artifacts/associative-drawing-ccbfb52e/report.json`.
Прогон связанной сборки: `artifacts/linked-assembly-b4aad7b0/report.json`.
Оба имеют `passed: true`. Область доказанного и дополнительные результаты:
`docs/coverage.md`. Локальные отчёты и CAD-файлы исключены из Git.

Живые проверки запускаются в интерактивном сеансе Windows того же пользователя,
что запустил КОМПАС. Они создают свои документы и закрывают только их:

```powershell
.\.venv\Scripts\python.exe scripts/validate_associative_drawing.py
.\.venv\Scripts\python.exe scripts/validate_linked_assembly.py
```

Каждый запуск оставляет отдельную папку с нативными файлами и `report.json`.
`passed: true` в отчёте означает прохождение всех проверок этого запуска.
Сценарий чертежа также сохраняет PNG до и после изменения.

## Следующий практический этап

Проверенные образцы простые: одна пластина, три проекции, один размер и одна
внешняя деталь в сборке. Это не подтверждает произвольные сложные модели,
вложенные сборки, сопряжения, спецификации или соответствие чертежа всем требованиям ЕСКД.
Для переноса на реальный проект нужны комплект связанных M3D/A3D/CDW и конкретные
изменения размеров/состава. Сначала изучаем структуру и зависимости, затем делаем
рабочую копию комплекта и проверяем изменения после повторного открытия.
Производственные документы остаются вне публичного репозитория.
